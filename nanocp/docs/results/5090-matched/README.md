# 双卡 RTX 5090 上的 GQA decode 复测

本次实验比较普通 DP、按请求分头的 head-TP 和本地 NanoCP-style CP。单位均为毫秒，表中延迟为两卡都完成时的 CUDA Graph 用时。测试从 Q 和当前步 KV 已就位开始，到两个 owner 的输出就绪结束。KV 初始放置、迁移、模型投影、MoE 和排队时间在测量窗口之外。

**方向建议**：保留 head-TP 作为消融，主线转向 GQA decode 的协作准入和长请求 KV 分配。优先验证本地 DP 与可变比例 CP 的选择能否在真实到达序列上改善进入 EP 之前的关键路径。十组主测试中，head-TP 的中位数均高于或贴近均分 CP。负载扫描中，伙伴从空闲到饱和时，最快选项依次经过均分 CP、偏向 owner 的 CP 和本地 DP。按页均衡已经能解释大部分选择，单靠长度阈值或可调比例的贡献有限。

[原始数据与正确性日志](measurements.tar.gz) 包含 201 条性能记录，保留每次 graph replay、主机用时、每卡 kernel 和阶段计时。`matrix-fixed` 为十个主测试，`load-fixed` 与 `ratio-fixed` 为七档负载，`equal` 与 `equal-ratio` 为等 token 对照。负载扫描的首轮在一个代表性输入上做 FP32 对拍，主表逐格对拍。

## 环境和复现

两张 RTX 5090，每卡 32 GB、170 SM。驱动 615.71.09，PyTorch 2.14.1+cu130，使用 PCIe memcpy 路径。16 个 Q 头、2 个 KV 头、head dim 256，bf16，页长 16。FA2 使用面向 sm80 的 PTX 在 sm120 上 JIT。保留服务器原有工作目录，本次独立运行目录为 `/root/bench-runs/matched-WTVd1i`。

起始代码为 vLLM `c4fe69224c`、测试 `975803df47` 和 FA fork `1b2248b`。在此基础上，FA fork 增加了 split-KV combine 写回与发布之间的 CTA 同步；测试仓库增加了相应的回归与负载、切分比例扫描。原扩展 SHA-256 为 `cc5a7797c14ab3712b1bf52dfa9a476509c653de1c62bfaffcc1c0987e434e7b`，修正版为 `eb5eb5d9661483bf228b55d6def7e4bd06b73aa96256b64b842b9c22b8865495`。

原扩展通过四个小样例，但在伙伴有 512 条短请求时，head-TP 相对 FP32 有 31 个元素绝对误差超过 0.01，最大误差 0.01838。将 Q 逐次变号，直接比较伙伴算出的头和回传到 owner 的头，100 次 replay 中有 3 次逐位不一致。错误在伙伴的回传缓冲即可观测。加入块内同步后，同一压力测试 100/100 次逐位相等，独立的双卡回归也通过。

从 `nanocp/bench_decode_cp` 运行以下命令。固定 `P2P_BACKEND=memcpy`、`OMP_NUM_THREADS=6`，用 `VLLM_ROOT` 和 `FLASH_ATTN_ROOT` 指向对应源码，让 Python 加载修正后的扩展。

```bash
python test_e2e_correctness.py
python bench_perf.py --check --rounds 30 --profile-rounds 3
python bench_partner_load.py
python bench_partner_load.py --cp-owner-percent 50 75 90
python bench_partner_load.py --equal-tokens
python bench_partner_load.py --equal-tokens --cp-owner-percent 75 90
```

主表每种方法每个输入测 30 次 replay，报告中位数。负载扫描每格重建图三次，轮换执行顺序，报告三个中位数的中位数。每张图另采三次 CUPTI 和三次带 external events 的阶段计时。两卡阶段有重叠，诊断图的 event 也有开销。

## 基线边界

本地 CP 使用与 head-TP 相同的 FA2、tile planner 和物理传输后端，按输入的页切分路由 Q、回传并合并 O/LSE。补齐作者固定的 FA3、DLSlime 等依赖后，原生双进程 GQA 在两卡建立 CUDA IPC 映射时均失败，独立调用原版 FA3 也缺少 sm120 可执行 kernel。原生延迟记为 N/A。在同一机器上，作者的 GQA forward 使用项目适配的 memcpy 和 FA2 默认 split 后已通过单请求和十组固定 batch 的双卡测试。[默认实现补测与匹配对照](native-default.md)

上游策略本身会根据空闲页分配 token，论文里的对照还应包括这种可变比例放置。[上游 SPStateManager](https://github.com/nano-infra/NanoEngine/blob/8abce29fe3ba0af3cd785b5e533b5b4b22ae70d5/csrc/nanodeploy/scheduler/sp_state_manager.cpp#L425-L501)

## 为什么伙伴负载能改变选择

固定 owner 为 4×65,536 加 128×256，CP 均分四个长请求，每一行只改变伙伴的 512-token 请求数。以下为诊断图中各 rank 的 attention 阶段，包含该流在此阶段的等待。

| 伙伴请求数 | Owner attention (ms) | Partner attention (ms) |
| ---: | ---: | ---: |
| 0 | 0.256 | 0.195 |
| 128 | 0.258 | 0.308 |
| 256 | 0.256 | 0.396 |
| 384 | 0.257 | 0.492 |
| 512 | 0.258 | 0.577 |
| 1024 | 0.257 | 0.922 |
| 2048 | 0.257 | 1.690 |

Owner 的工作量相同、阶段时间也稳定。伙伴从空闲变成瓶颈后，继续把一半 KV 分给它会延迟两卡一起完成的时间。实际准入需要估计两边本步的完成时间，再与保持本地以及移动或远程放置 KV 的成本比较。

## 原十组输入的复测

三种方法使用相同的双卡原始 Q/K/V。30 个方法与用例组合均通过两个 owner 的 CPU FP32 对拍，绝对误差阈值为 0.01。末行两张卡各有 1024 条短请求，owner 另有四条长请求。单图内的 30 次 replay 描述该图的波动，接近的数值应视为持平。

| 20×32768 | 0.839 | 0.567 | 0.503 |
| 128×8192 | 1.341 | 0.844 | 0.833 |

## 固定 owner，改变伙伴的短请求数

CP 列标识 owner 保留的比例。50% 列取三种方法轮换的实验，75% 和 90% 列取切分比例轮换的实验。每格有三次独立建图，每次 30 次 replay。

| 伙伴请求数 × 512 token | DP | head-TP | CP 50% | CP 75% | CP 90% |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0 | 0.422 | 0.376 | **0.286** | 0.369 | 0.417 |
| 128 | 0.425 | 0.450 | **0.366** | 0.370 | 0.417 |
| 256 | 0.425 | 0.541 | 0.445 | **0.370** | 0.416 |
| 384 | 0.426 | 0.640 | 0.547 | 0.445 | **0.417** |
| 512 | **0.428** | 0.727 | 0.626 | 0.539 | 0.601 |
| 1024 | **0.721** | 1.084 | 0.977 | 0.904 | 0.800 |
| 2048 | **1.384** | 1.785 | 1.734 | 1.642 | 1.475 |

以简单的等 KV 页数策略估计还剩多少改进空间。设长请求 token 总数为 L，owner 和伙伴本地短请求分别有 A、B 个 token，两卡等容量。令两卡最终 KV token 数相等，求得 owner 应保留的比例为 `0.5 + (B − A) / (2L)`。映射到最近的可选比例 50%、75%、90%、100%，100% 走 DP。七档各执行一步，这个策略合计 4.173 ms，事后逐档任选最优方案合计 3.971 ms，对应 **4.82% 的整图延迟改进上限**。差距主要来自 512 档的 0.601 对 0.428 ms。这个估算使用本实验的候选集和等权重，未计决策与迁移成本。作者调度器还含准入、rank 选择等逻辑，此处只复现按页均衡的直觉。

## 固定伙伴的 token 和页数

下面三档伙伴均有 131,072 个历史和当前 token，按 16-token 页计均占 8,192 页。分片前的 owner 和前表相同。对每组物理输入，各方法的 Q/K/V 一致。

| 伙伴请求数 × 每条长度 | DP | head-TP | CP 50% | CP 75% | CP 90% |
| --- | ---: | ---: | ---: | ---: | ---: |
| 64×2048 | 0.426 | 0.519 | 0.439 | 0.418 | 0.418 |
| 256×512 | 0.428 | 0.541 | 0.447 | 0.370 | 0.419 |
| 1024×128 | 0.427 | 0.718 | 0.538 | 0.418 | 0.419 |

CP 75% 相对 DP 的整图降幅分别为 1.9%、13.5% 和 2.2%。64×2048 的 CP 75% 三轮为 0.406、0.418、0.420 ms。结果支持将行数或长度分布加入收益估计；这三档没有建立最优方法随行数稳定反转的证据。只有收益足够覆盖通信、KV 放置及调度开销的请求才值得协作。

## 下一步实验

1. 在现有 trace replay 中记录入队时两卡的请求数、长度分布、驻留页与空闲页、预计参与的全 attention 层数。预先决定验证集，分别覆盖伙伴空闲、切换区间和两边都忙的 step。
2. 用实机 profile 估两卡的 attention 时间和通信成本，在本地与几个合法 CP 比例中选择。固定准入时刻，将一次性 KV 放置或迁移成本按预计剩余 decode 步数摊销。策略先在离线 trace 上对照普通 DP 放置、固定 CP 和按可用页分配的强基线。
3. 按真实 step 频率报告事后最优上限，再报告策略实际拿到的收益、决策开销、激活率和回退次数。有稳定净收益后，接入真实 DP-attention + EP 服务，测 SLO 下吞吐、P95/P99 TPOT 和进入 EP 前的等待；若强基线已接近该上限，则停止扩展这个策略。
