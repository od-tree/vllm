# 2×RTX 5090 上的 head-TP 与 NanoCP

同一组 case、同一套 Qwen3.5 GQA 规格：16 Q / 2 KV，`head_dim=256`，bf16，page 16，`d=2`。单位是毫秒。

机器是 2×RTX 5090（sm_120，170 SM，各 32 GB）。FlashAttention 2 只编了 bf16 head-dim 256，二进制是 sm_80 PTX，在 5090 上 JIT。两卡之间 kernel 直写对端地址不可用，传输是 `cudaMemcpyPeer`。

## 为什么上一张表慢

上一张表里 head-TP 是主机墙钟，NanoCP 是 GPU0 上流上的事件，而且那次事件没有等 GPU1。两边都没有 CUDA Graph。

head-TP 带通信在 5090 上是 send、compute、splice 三次启动，中间两次主机同步，再加若干次同步的 `cudaMemcpyPeer`。纯长的小 batch 上，这些空隙比 attention 本身大。`20x32768` 从 2.528 ms 降到 1.094 ms，多出来的大约 1.4 ms 就是这些空隙。compute 和 splice 各算一遍本卡那一个 KV head，串起来大约等于单卡一次全 head。所以大 batch 去掉空隙之后，带通信可以接近甚至略低于单卡，例如 `256x32768` 的 10.882 对 11.751。A100 上是一次融合 kernel，这里的比值仍然不能直接当成 A100 的比值。

NanoCP 更明显。路由按 token 调用同步的 `cudaMemcpyPeer`，1024 的 batch 是几千次主机往返。`mix_1024x1024_4x256k` 从 64.561 ms 降到 6.482 ms。合并 kernel 一直在 0.1 ms 左右，不是慢的来源。图里仍保留原来的逐行拷贝和回传 staging，只是不再每次从 CPU 启动。`cudaMemcpyPeerAsync` 在捕获期间会失败，图内拷贝用的是对端指针上的 `cudaMemcpyAsync`。

合并列仍是预热后那一次 eager `combine_kv` 的 GPU 时间。这台驱动上，录进图里的 event 不能再 `elapsed_time`。这个 kernel 只有一个，图不会改变它的 GPU 时间。

## 列定义

- 单卡：整段 KV 在原卡上的 FA2。
- 无通信：`src_rank=-1`，只切 KV，不交换。
- 带通信：5090 的 send、compute、splice，拷贝在图里。
- NanoCP：Q 路由、两侧 FA2、O/LSE 回传和合并。KV 在计时前已经放在各自的卡上。

`mix_1024x1024_4x256k` 的伙伴卡自己还有 1024 条短请求。图的单卡列只报原卡。

## 正确性

门槛是 bf16 最大绝对误差 `1e-2`。这次图计时前，head-TP 的 `check_mix`（`[64, 96, 128, 17]`）仍然通过。正确性数字来自图之前的 eager 跑法。

| 检查 | 最大绝对误差 |
| --- | --- |
| FA2 两半合并，单卡两个逻辑 rank | `4.9e-4` 到 `3.9e-3` |
| 两卡 e2e，`[128]`、`[100]`、`[64, 96, 128, 17]` | `2.0e-3` 到 `3.9e-3` |
