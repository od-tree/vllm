# 2×RTX 5090 上的 head-TP 与 NanoCP

同一组 case、同一套 Qwen3.5 GQA 规格：16 Q / 2 KV，`head_dim=256`，bf16，page 16，`d=2`。单位是毫秒。

机器是 2×RTX 5090（sm_120，170 SM，各 32 GB）。FlashAttention 2 只编了 bf16 head-dim 256，二进制是 sm_80 PTX，在 5090 上 JIT。两卡之间 kernel 直写对端地址不可用，传输是 `cudaMemcpyPeer`。

纯长 batch 里 head-TP 打平或更快，`256x32768` 是 5.478 对 6.128。长短混合里 NanoCP 仍快约 15%，`mix_512` 和 `mix_1024` 已经收到 1.02 和 1.07。NanoCP 这一列没有重跑。

## tile

旧规则把每个长行的 split 卡在 16。NanoCP 每个长行有 2 个 KV head，16 个 split 仍能放出 32 个 CTA。head-TP 每个长行只有 1 个 KV head，两个长行一共 32 个 CTA，170 个 SM 填不满。`mix_32` 的 attention 因此是 0.937，NanoCP 是 0.479。

现在长行按自己的 KV 字节占这一步总 KV 的比例，分到一轮 SM。head 越少，每个长行的 split 越多，两边的 CTA 数都接近 170。短行已经占住的 SM 要扣掉：`mix_1024` 有 1024 条短请求，再把长行拆到 40 份以上不会少读字节，只会把 combine 从 0.15 ms 抬到 0.43 ms。多出来的 SM 只在所有最慢的长行都能再分到一份时才用，避免一部分行拆了、最慢的那行却还是整段 KV。split 上限是 127，因为 `row_splits` 是 int8，FA2 的 combine 也只编到 128 份。

改完之后这几行的 attention（较慢那张卡，ms）：

| case | head-TP compute | NanoCP FA2 |
| --- | ---: | ---: |
| mix_128x256_2x128k_1x256k | 0.382 | 0.382 |
| mix_64x1024_4x128k | 0.444 | 0.421 |
| mix_32x512_2x256k | 0.369 | 0.356 |
| mix_1024x1024_4x256k | 1.960 | 1.953 |

`mix_32` 和 `mix_128` 的 attention 已经对齐。交换以前按整个 batch 拷 Q/K/V/O 平面，两个方向都拷。短行不会被对端读，`mix_1024` 因此把 4 条长行放大成 1028 个 token，关键路径上大约 19 MB。现在只拷长行前缀，而且只走对端会读的方向：compute 前是 owner 到伙伴卡，splice 前是伙伴卡的输出回到 owner。`mix_1024` 的这 6 次拷贝是 0.006 ms。

剩下的墙钟差主要是 `fa2_combine`。`mix_32` 是 0.040 对 0.021，`mix_128` 是 0.102 对 0.051，`mix_1024` 是 0.151 对 0.076。`mix_1024` 两边 owner 的 FA2 都是 1.96 ms。head-TP 的伙伴卡也是 1.960 ms，因为它拿的是长行的另一个 KV head、整段 token，再加上自己的 1024 条短请求。NanoCP 的伙伴卡是 0.669 ms，因为它只有长行的后半段、两个 KV head，短请求留在 master。这段和 owner 重叠，不单独加到墙钟上。

纯长 batch 本来就能填满 SM，split 数没变。

## 列定义

- 单卡：整段 KV 在原卡上的 FA2。
- 无通信：`src_rank=-1`，只切 KV，不交换。
- 带通信：send、compute、splice。splice 是单独的拷贝 kernel。
- NanoCP：Q 路由、两侧 FA2、O/LSE 回传和合并。KV 在计时前已经放在各自的卡上。活跃行打包成一次拷贝。

`mix_1024x1024_4x256k` 的伙伴卡自己还有 1024 条短请求。图的单卡列只报原卡。

## 正确性

门槛是 bf16 最大绝对误差 `1e-2`。只拷长行前缀之后 head-TP 的 `check_mix`（`[64, 96, 128, 17]`）仍通过。NanoCP 两卡 e2e 的最大绝对误差是 `2.0e-3` 到 `3.9e-3`。
